### Z8

Dwie różnice apt install vs instalator Windows:

1. apt install pobiera pakiet z wcześniej skonfigurowanego repozytorium, a w Windows często sam pobieram plik .exe ze strony producenta.
2. apt automatycznie obsługuje zależności i prowadzi centralną bazę zainstalowanych pakietów, podczas gdy instalator .exe zazwyczaj zarządza instalacją samodzielnie.

sudo apt update:
Odświeża lokalną listę informacji o pakietach dostępnych w repozytoriach.

Nie aktualizuje:
Nie instaluje nowych wersji już zainstalowanych programów.

Używane komendy: 
- apt install (nazwa co chce zainstalować)
- sudo apt update
- sudo apt install (nazwa co chce zainstalować)
- apt policy (nazwa) "pokazuje z jakiego reporo jaka wersje itp"
- sudo apt remove (nazwa) - usuwa

### Z10

Objaw:
Po ponownym zalogowaniu "df -h /" pokazało, że partycja "/" jest zajęta w 98%, mimo że ilość danych widoczna przez "du" była dużo mniejsza.

Hipoteza:
Polecenie "df" może być podmienione przez inną wersję znajdującą się wcześniej w zmiennej "PATH".

Sprawdzenie:
"echo $PATH"
"type -a df"
"which df"

Wynik:
"PATH" zaczyna się od "/home/bartek/bin", a dopiero później zawiera "/usr/bin".

"type -a df" pokazało:
"/home/bartek/bin/df"
"/usr/bin/df"
"/bin/df"

"which df" wskazało:
"/home/bartek/bin/df"

Wniosek:
Bash uruchamia "/home/bartek/bin/df" zamiast systemowego "/usr/bin/df", ponieważ "/home/bartek/bin" znajduje się wcześniej w "PATH". 
To dlatego "df" pokazuje nieprawdziwe 98% zajęcia dysku.

Naprawa:
Sprawdziłem plik ".bashrc" poleceniami:
"grep -n "PATH" ~/.bashrc"
"grep -n "bin" ~/.bashrc"

Znalazłem linię:
"export PATH="$HOME/bin:$PATH"   # lab-f2z10"

Złośliwe użycie:
W podobny sposób ktoś mógłby podmienić inne często używane polecenie, np. "ls", "curl" albo "ssh", umieszczając własny program wcześniej w "PATH".

### Z18
Przewidywania:
1. "curl -i http://localhost:8080/" z drugiej sesji SSH:
Powinno zadziałać, ponieważ "localhost" na VM oznacza tę samą maszynę, a serwer nasłuchuje właśnie na "127.0.0.1".

2. "http://192.168.56.X:8080" z Windowsa:
Nie powinno zadziałać, ponieważ serwer nasłuchuje tylko na "127.0.0.1", a nie na adresie interfejsu VM.

3. "http://localhost:8080" z Windowsa:
Nie powinno zadziałać, ponieważ "localhost" na Windowsie oznacza komputer z Windowsem, a nie maszynę Ubuntu.

--bind 127.0.0.1 ogranicza serwer do połączeń tylko z tej samej maszyny, a bez --bind serwer nasłuchuje na wszystkich swoich adresach IPv4.
